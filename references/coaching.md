# 调教手册：brief 模板、反馈写法、常见失败模式

## 1. Brief 模板（复制后替换尖括号）

```
【先读】<要它读的文件的完整路径>

【背景】<一两句：这是什么项目，上一版哪里不行>

【目标】<一句话>

【必须做到】
- <具体内容 1：能被检查的>
- <具体内容 2>

【不要做】
- <不碰的文件或目录、不允许的捷径（比如改测试让它通过）>

【阶段】
1. <阶段 1>：交付 <具体产出>。做完停下，等我确认。
2. <阶段 2>（等我确认后再做）

【验收（每个阶段都要满足，汇报时贴证据）】
1. <命令> 的输出满足 <条件>
2. <文件 / 页面 / 图片> 里能看到 <内容>
3. 列出最弱的 2 个地方和原因；能修的先修再交。

【汇报格式】做了什么 / 改了哪些文件 / 怎么验证的（命令 + 输出）/ 最弱的地方。
```

复述确认用单独的一轮（`effort: low`）：

```
读完 <文件>，用 3–5 句话复述：目标、你要遵守的规则、第一阶段要交什么。
只复述，不要修改任何文件，等我确认后再开始。
```

## 2. 反馈写法

| 不好 | 好 |
|---|---|
| "测试没过，修一下" | "`pytest tests/test_api.py::test_login` 失败：期望 401，实际 500（贴报错）。先找根因写进汇报，再修；不要改测试本身。" |
| "页面在手机上有问题" | "`/pricing` 在 375 px 宽下横向溢出：`.plan-table` 固定宽度 720px（`styles.css:212`）。改成可横向滚动的容器或响应式布局。验收：375 px 宽截图里没有横向滚动条。" |
| "数据不对" | "`scripts/export.py` 输出 9,812 行，源表是 10,000 行；丢的 188 行都是 `country` 为空的记录（附查询）。保留这些行，`country` 写成 `unknown`。验收：输出行数 = 源表行数。" |
| "细节不够，再丰富一点"（3D 渲染项目） | "01 镜里 60% 画面是没有结构的平面（附原分辨率裁切）。前排建筑要有楼层带和窗格这类真实几何。验收：项目的细节检查脚本对这张图判定通过。" |
| "整体不错，有几个小问题"（列了 12 条） | 只列最重要的 3 条，其余写"下一轮再看"。 |
| 直接贴一大段代码让它粘贴 | 说明要改的函数、期望行为、约束和验收方式，让它自己实现。 |

## 3. 常见失败模式和对策

| 现象 | 根因 | 对策 |
|---|---|---|
| 提前宣布"全部完成" | 没有可检查的验收标准；它只跑了部分测试 / 只看了缩略图 | brief 里写死验收命令，要求贴输出；你自己复查 |
| 把问题写进 README 或说明，然后照样交付 | 没有"先修再交"的要求 | 明确"最弱的地方先修，修不了说为什么" |
| 时间全花在次要环节（调参数、调样式） | 需求里次要目标写得比主要目标具体 | 分阶段，规定顺序（先结构、再细节、最后润色），每阶段单独验收 |
| 越改越乱，堆一堆 `patch_*.py` / `fix_*.py` | 没有版本管理，补丁式修改 | 要求直接改主文件，每个阶段 git 提交一次 |
| 报错后假装成功 | 没人看工具结果 | 用 `dsh_history` 看 tool result，要求汇报里贴原始输出 |
| 早期规则在后期被忘 | 会话过长，上下文被挤掉 | 新会话 + 新 brief；规则放开头、验收放末尾 |
| 同一个错反复出现 | 反馈不具体，或模型能力不够 | 给位置 + 期望 + 验收；两轮无效就缩小任务或换模型 |
| 在不确定时自己猜用户偏好 | brief 没说遇到不确定怎么办 | 写明"遇到 <某类> 决定就停下来问" |
| 越权尝试被拒后卡住 | 任务确实需要工作区外的权限 | 问用户是否允许；或者调整任务，让它不需要越界 |

## 4. 一个完整循环（例：给命令行工具加一个参数和测试）

1. 用户："让 DeepSeek 给 `tool` 加一个 `--dry-run` 参数，带测试。"
2. 你：读代码结构 → 确认 `cwd` 是干净的 git 仓库 → 定验收标准（新测试通过、旧测试不退化、`--dry-run` 不写任何文件）→ 写 brief，第一阶段只要参数解析和测试。
3. `dsh_start` → `dsh_wait`（可能要调用多次）→ 它说"完成，测试全部通过"。
4. 你：`git diff --stat`，发现它还改了 `setup.cfg`；自己跑 `pytest`，新测试过了，但一个旧测试被它标成了 skip；`dsh_history` 显示它第一次跑时那个测试失败过。
5. 反馈："撤销 `setup.cfg` 的改动；恢复被 skip 的 `test_config_merge` 并修好根因；验收：`pytest` 全部通过且没有 skip。"
6. 第二轮达标 → 派第二阶段（文档和 `--help` 文案）。
7. 向用户汇报：哪些是你亲自验证的、测试数字、改了哪些文件，以及它曾经试图跳过一个测试。
